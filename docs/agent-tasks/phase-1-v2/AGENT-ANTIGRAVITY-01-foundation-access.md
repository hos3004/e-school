## طريقة العمل الملزمة

- النطاق معتمد. اكتب خطة قصيرة داخل المحادثة ثم **ابدأ التنفيذ ولا تتوقف لطلب اعتماد الخطة**.
- اسأل فقط عند مانع حقيقي قد يسبب فقد بيانات أو ضعف أمان أو يحتاج سرًا خارجيًا.
- لا `git commit` ولا `git push`.
- افحص `git status` قبل كل مجموعة تعديلات ولا تكتب فوق تغييرات لا تخصك.
- كل PHP/Composer/Artisan داخل Docker.
- لا تشغّل Pest على قاعدة التطوير أو قاعدة اختبار مشتركة مع وكيل آخر.
- لا تعلن الإتمام من اختبارات مصطنعة، Gates اختبارية، أو Policy موسّعة بلا سند.

## الهدف القابل للتحقق

تسليم أساس مستقر يسمح ببدء بقية المرحلة:

1. التصفح المحلي سريع ومستقر بقياس قبل/بعد.
2. الاختبارات لا تغيّر بيانات التطوير ولا تتصادم في PostgreSQL/Redis/queues.
3. Admin/Supervisor/Teacher/Student يملكون حسابات مستقلة وواجهات وصول صحيحة.
4. منح وسحب الصلاحيات يعمل من الواجهة ويُطبّق Server-side.
5. لا يمكن لمستخدم الوصول إلى كائن أو قائمة تخص مؤسسة أخرى.

## 1. جرد صادق قبل التعديل

سجّل في التقرير:

- حالة Docker الفعلية والـmounts وموارد الحاويات، لا الافتراضات.
- زمن warm TTFB لثلاث محاولات على `/up` و`/admin/login` وصفحة طلاب وصفحة معلمين.
- عدد الاستعلامات في صفحتي الطلاب والمعلمين ولوحة الإدارة.
- إعداد OPcache وPHP-FPM ووجود Xdebug من عدمه.
- قواعد البيانات وRedis prefixes/queues التي تستخدمها development وtesting الآن.
- مسارات الدخول والبوابات والموارد الفعلية من `route:list`.
- كل Policy/permission mismatch مؤكد مع اختبار إنتاجي لا Gate مختلق.

المعروف من التشخيص السابق ويجب التحقق منه قبل الإصلاح:

- Windows bind mount الكامل يجعل metadata للتابعيات بطيئة جدًا.
- `validate_timestamps=1` مع `revalidate_freq=0` يضاعف تكلفة الـmount.
- PHP-FPM يصل إلى `pm.max_children=5` عند التوازي.
- قوائم الجغرافيا قد تنفذ مئات الاستعلامات في صفحة الطلاب/التسجيل.
- تسجيل Gates وفحص كل صلاحية قد ينفذ عشرات الاستعلامات لكل طلب.
- `config/modules.php` يفعّل Payroll حاليًا، و`AdminPanelProvider`/Dashboard widgets
  تسجل موارده وأرقامه؛ أخفها خلف flags بدل حذف الكود.
- `modules/Integrations/database/Seeders/IntegrationsSeeder.php` يزرع Zoom كتكامل
  فيديو نشط؛ هذا مخالف لقرار BBB-only ويجب ألا يبقى نشطًا أو ظاهرًا.

## 2. الأداء

نفّذ أصغر حل مستقر، مع الحفاظ على تجربة التطوير:

- أخرج `vendor` و`node_modules` من NTFS bind metadata path باستخدام named volumes/image،
  أو وثّق وشغّل مسار WSL2 ext4 إذا كان هو الحل المعتمد للبيئة.
- لا تخفِ كود المشروع عن hot reload المطلوب؛ فرّق بين source والتابعيات.
- اضبط OPcache للتطوير بفترة إعادة تحقق معقولة، والإنتاج بإعداد منفصل موثق.
- ارفع FPM workers محليًا بما يناسب الذاكرة بعد القياس؛ هذا لتحسين التوازي وليس لإخفاء طلب بطيء.
- اجمع قراءة الدول والمناطق بدل الاستعلام داخل كل row/render/filter.
- أضف request-scoped memoization آمنًا لفحص الصلاحيات، ولا تجعل Cache قديمًا يسمح بوصول مسحوب.
- خفف استعلامات Dashboard المتكررة وNavigation badges المثبتة فقط.
- لا تجعل خطًا خارجيًا render-blocking؛ استخدم أصلًا محليًا أو fallback مناسبًا.
- فعّل caches الآمنة للبيئة المناسبة، مع أوامر clear/rebuild موثقة.

### قبول الأداء

- تقرير قبل/بعد بنفس الجهاز ونفس البيانات، والاختبارات متوقفة أثناء القياس.
- ثلاث قياسات warm لكل مسار، مع median وp95 إن أمكن.
- هدف محلي إرشادي: median TTFB أقل من ثانيتين للصفحات البسيطة وأقل من 3 ثوانٍ
  للقوائم الممثلة. إن منع عامل خارجي ذلك، اثبت العامل بالأرقام ولا تدّع النجاح.
- صفحة الطلاب/المعلمين لا تعيد الاستعلام لكل صف ولا تتجاوز ميزانية استعلامات يحددها
  التقرير من القياس الجديد وتُحرس باختبار regression.
- لا regression في البحث أو فلاتر الدولة/المنطقة أو الصلاحيات بعد التجميع.

## 3. عزل الاختبارات

أنشئ مسارًا واضحًا لا يمكن أن يلمس development بالخطأ:

- PostgreSQL testing مستقل أو قواعد فريدة لكل run/agent، لا `eschool_testing` مشتركة.
- Redis database/prefix وqueues مستقلة للاختبار.
- `APP_ENV=testing` و`CACHE/SESSION/QUEUE/MAIL` آمنة ومحددة صراحةً.
- guard يفشل سريعًا إن حاول test runner استخدام اسم قاعدة development/production.
- أمر موثق للاختبار الموجّه، وأمر للجولة الكاملة، وأمر للتنظيف الآمن.
- CI يستخدم نفس المبدأ ولا يعتمد على ملفات محلية مستثناة من Git فقط.
- تشغيلين متزامنين لا يسقط أحدهما migrations الآخر ولا يستهلك jobs الخاصة به.

لا تستخدم حذفًا عامًا أو glob غير متحقق. أي تنظيف يستهدف قاعدة/حاوية اختبار محددة فقط.

## 4. الحسابات والواجهات حسب الدور

- ملكية هذه المهمة هي `User` والمصادقة والاستعادة والأدوار. استخدم Profiles الموجودة
  كfixtures لإثبات الوصول؛ دورة إنشاء/تعديل StudentProfile وStaffProfile يملكها Task 02.
- نموذج هوية واحد وحساب مستقل لكل شخص، مع Profile مناسب لا جداول users متعددة.
- Admin/Supervisor/Teacher/Student يدخلون ببياناتهم ويصلون إلى landing page مناسبة.
- إعادة التوجيه والواجهة مبنيان على permissions/capabilities، لا `if role === ...`.
- username إلزامي وفريد، والبريد أو الهاتف حسب قواعد التسجيل؛ الاستعادة عبر القناة المتاحة.
- استعادة البريد تعمل فعليًا. للحساب phone-only ابنِ token/OTP آمنًا خلف عقد قناة،
  مع expiry/one-time-use/rate limit ومنع account enumeration، وأطلق طلب التسليم عبر
  الإشعارات. Task 04 يملك ربط العقد بـWhatsApp الحقيقي؛ لا تستدعِ Meta من Identity.
- لا يمكن إنشاء حساب مكرر لنفس الشخص بسبب اختلاف البريد/الهاتف.
- صفحات الحساب تعرض وتعدّل البيانات التي يملك المستخدم صلاحيتها فقط.
- حافظ على Guardian الحالي وقاعدة منعه من محادثات الطالب الخاصة.

الصفحات الدنيا المطلوب إثباتها:

- تسجيل الدخول، الخروج، الاستعادة، ورسائل الخطأ المترجمة.
- إدارة المستخدمين والحسابات والربط بالملف.
- إدارة الأدوار والصلاحيات والمنح المباشر إن كان مدعومًا.
- Dashboard لكل دور أساسي مع رفض الدور غير المسموح.

## 5. الصلاحيات وعزل المؤسسة

- وحّد أسماء الصلاحيات بين المصفوفة والSeeder والPolicies والواجهات.
- كل مورد جديد/حالي ضمن هذه المهمة له Policy مسجلة وobject-level authorization.
- لا تعتبر إخفاء زر حماية؛ حاول URL/HTTP مباشرة في اختبارات الرفض.
- لا `Gate::define` داخل test ليجعل السيناريو أخضر إذا لم يكن Gate موجودًا في الإنتاج.
- افصل صلاحية `viewAny` عن `view/update/delete` عند اختلاف النطاق.
- كل queries للقوائم والتصدير والبحث محكومة بالمؤسسة، لا صفحات التفاصيل فقط.
- اختبر مؤسستين ومستخدمين بأدوار متشابهة، وحاول الوصول بالـID المباشر والتصفية والتصدير.
- تغييرات الدور/الصلاحية Audit مع actor/before/after/reason، ويظهر أثر السحب فورًا.
- لا تضف Super Admin bypass خفيًا؛ أي تجاوز موثق في Policy ومصفوفة الصلاحيات.
- أبقِ Payroll/Billing/Payments خلف feature/module flags وأخفِ صفحاتها وأفعالها من
  واجهات المرحلة الأولى، دون حذف كود المال أو إضعاف ضوابطه.
- أزل/عطّل أي seed أو Integration نشط يعلن Zoom مزودًا معتمدًا. لا تنفّذ BBB هنا؛
  فقط لا تسمح لبيانات demo أو الواجهة بمخالفة قرار BBB-only قبل Task 03.

## اختبارات القبول الإلزامية

1. Development data تبقى كما هي بعد تشغيل suite معزولة.
2. تشغيل مجموعتين من الاختبارات بالتوازي بلا DDL collision أو Redis leakage.
3. حساب من كل دور يدخل ويرى صفحته، ودور خاطئ يأخذ 403/404 الصحيح.
4. منح صلاحية ثم سحبها يغير النتيجة دون restart أو Cache stale.
5. مستخدم المؤسسة A لا يرى قائمة أو سجلًا من المؤسسة B عبر UI أو HTTP أو ID مباشر.
6. اختبار permission حقيقي يفشل لو حُذفت Policy/Gate الإنتاجية.
7. benchmark قبل/بعد مع query counts، وregression tests لأسباب البطء المصححة.
8. `route:list`، اختبارات Architecture/ownership المتأثرة، وPint/PHPStan الموجّه تمر.
9. لا تظهر قوائم أو أفعال مالية لأي دور ضمن تسليم المرحلة الأولى.
10. استعادة البريد تمر كاملة، واستعادة phone-only تثبت إنشاء/تحقق/انتهاء/منع إعادة
    استخدام الرمز عبر Fake contract؛ ويسجل التقرير صراحة أن النقل الحقيقي يملكه Task 04.
11. لا يوجد Zoom integration نشط أو ظاهر في seed/واجهة المرحلة الأولى.
