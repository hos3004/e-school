## الهدف القابل للتحقق

رحلة واجهة كاملة:

`إنشاء برنامج وتصنيف داخله ودورة مرتبطة ومجموعة → إنشاء/تأهيل معلم → تقديم طالب من النموذج العام →

كل خطوة تحفظ العلاقة الصحيحة وتطبق الصلاحيات وعزل المؤسسة والتدقيق.

## 1. جرد الواقع

قبل التعديل، أثبت في التقرير:

- موارد وصفحات ومسارات Students/Staff/Academics/Groups/Enrollments الموجودة فعليًا.
- أي Resource بلا `getPages()` أو زر بلا Action أو نموذج لا يصل إلى Controller/Action.
- الجداول والعلاقات والعقود المنفذة ومَن يملك كل جدول.
- حالات `RegistrationApplication` و`Enrollment` وعضوية المجموعة الفعلية.
- ما تم من الجغرافيا والأهلية وteacher qualifications والإتاحة، مع الاختبارات القائمة.
- الفجوات بين UI payload وFormRequest/Action؛ لا تعتبر API موجودًا دليل إتمام الواجهة.

## 2. الطلاب والمعلمون

- Task 01 يملك `User` والمصادقة. هذه المهمة تملك دورة حياة StudentProfile/StaffProfile
  وربطهما بالحساب، وتستدعي Identity عبر عقد عام عند إنشاء حساب من نموذج التسجيل.
- قائمة/عرض/إنشاء/تعديل/تعليق واستعادة ملفات الطلاب والمعلمين وفق الصلاحيات.
- ربط كل Profile بحساب Identity مستقل ومنع التكرار أو orphan profile.
- دولة ومنطقة وبيانات الاتصال والحالة والجنس/العمر حيث تتطلب قواعد الأهلية.
- تأهيل المعلم لدورة أو مادة بعقد عام يستهلكه التسكين والجدولة لاحقًا.
- إتاحة المعلم: أيام، أوقات، timezone، recurrence، استثناءات، إجازات وحالة اعتماد.
- إتاحة الطالب بنفس الأساس، مع Query يعيد الخانات المشتركة دون تسريب Models.
- تخزين UTC وعرض توقيت المستخدم، والترجمة العربية RTL مع en/fr حسب القاعدة الحالية.
- SoftDeletes/تعليق بدل الحذف، وAudit للتعديل الحساس.
- استيراد Excel للطلاب والمعلمين والبيانات الأكاديمية الحالية: ملف آمن، mapping/preview،
  server-side validation، تقرير row errors، idempotency وعزل المؤسسة؛ لا mass assignment خام.

## 3. البنية الأكاديمية

- Program هو الجذر، وتصنيفاته/subcategories/tracks/levels مرنة؛ لا تعكس الاتجاه أو
  تستبدل العلاقات القائمة بسلسلة FK لمجرد تبسيط الواجهة.
- برنامج `fixed_duration` أو `ongoing`، وتواريخ صحيحة عند النوع الثابت.
- Course يرتبط ببرنامج وبأكثر من تصنيف عند الحاجة وفق النموذج الحالي.
- نوع الحصة `individual/group/both` والعمر والجنس والأهلية حسب إعداد البرنامج.
- إنشاء دورة جديدة من واجهة الإدارة داخل فئة برنامج موجودة.
- إنشاء Group كصف تشغيلي وربطه بالمؤسسة والبرامج والمعلمين وموادهم/دوراتهم وإعداداته.
- حافظ على `group_programs` وعلاقة المجموعة/البرنامج/المعلم many-to-many وteacher-course
  assignment القائمة؛ لا تضف `course_id` أحاديًا إلى Group. يمكن للدورة الظهور في
  عدة مجموعات، والمجموعة قد تخدم أكثر من برنامج/مادة حسب قرار العميل.
- العلاقات غير الصالحة والتجاوز الإداري تُرفض أو تحتاج صلاحية وسببًا وتدقيقًا.

لا تنفّذ أسعارًا أو اشتراكات أو مستحقات. وجود حقول قديمة لا يجعل المالية ضمن المهمة.

## 4. نموذج التسجيل العام والقبول

- صفحة عامة تعرض الدورات المفتوحة وتسمح باختيار دورة محددة.
- نموذج responsive مترجم مع CSRF وrate limiting وserver-side validation.
- يدعم المتقدم الجديد دون دخول إداري، ويربط بحساب موجود بأمان عند التطابق الموثوق.
- للمتقدم الجديد ينشئ/يستدعي إنشاء حساب Identity مستقل ثم RegistrationApplication؛
  لا ينشئ Profile قبل القبول، ولا يكتب Task 02 مباشرة في جدول `users`.
- كشف الطلب المكرر بالبريد/الهاتف/هوية الشخص وفق قواعد العميل دون دمج خاطئ لشخصين.
- الحالات واضحة: draft/submitted/under_review/accepted/rejected/waiting_assignment وما هو معتمد.
- قائمة إدارة للمراجعة والبحث والفلترة، وصفحة عرض تاريخ الطلب وبياناته.
- القبول/الرفض بصلاحية وسبب، داخل transaction وAudit، مع إطلاق Domain Event.
- انشر بعقود مستقرة: `registration.submitted` و`registration.approved` و
  `registration.rejected`; لا تمرر Eloquent Models في الحمولة.
- القبول ينشئ StudentProfile مرة واحدة فقط عند القاعدة المعتمدة؛ لا يسكّن تلقائيًا.
- إعادة تنفيذ Action أو webhook/request لا تضاعف الحساب أو الملف أو القيد.

## 5. القيد والتسكين

- افصل حساب المستخدم وRegistrationApplication وStudentProfile وEnrollment وGroupMembership.
- امنع التسكين قبل القبول على مستوى Action وقاعدة البيانات حيث يمكن، لا في الزر فقط.
- افحص أهلية البرنامج والدولة/المنطقة والعمر والجنس ونوع الحصة من الإعدادات.
- افحص السعة والتكرار والمؤسسة وحالة الطالب/المجموعة وتأهيل المعلم.
- استخدم الخانات المشتركة للإرشاد/التحقق دون بناء واجهة حجز ذاتي متقدمة غير مطلوبة.
- شاشة للمقبولين المنتظرين، اختيار البرنامج/الدورة/المجموعة والمعلم، ثم نتيجة واضحة.
- انشر `teacher.availability.approved` و`student.assigned_to_teacher` و
  `student.assigned_to_group` عند تحققها، مع organization/subject IDs وcorrelation ID.
- صفحة المجموعة تعرض بيانات الدورة والمعلمين والأعضاء والحالة والسعة؛ BBB يأتي في Task 03.
- النقل أو فك العضوية لا يمحو التاريخ، ويحتاج سببًا وصلاحية وتدقيقًا.
- استيراد Groups وmemberships من Excel يمر بالقبول والأهلية والسعة ومنع التكرار نفسها؛
  لا يكتب مباشرة في الجداول متجاوزًا Actions.

## اختبارات القبول الإلزامية

1. Admin ينشئ Program وتصنيفًا داخله، ثم Course مرتبطًا، ثم Group بعلاقات البرامج
   والمعلمين/المواد؛ وتظل العلاقات صحيحة بعد إعادة التحميل.
2. معلم بحساب مستقل يُؤهل للدورة وتُحفظ إتاحته في timezone مختلفة بصورة صحيحة.
3. زائر يقدّم لدورة متاحة؛ الطلب المكرر والمدخلات غير الصالحة وrate limit تُرفض.
   المتقدم الجديد يحصل على حساب مستقل وطلب مرتبط به دون إنشاء Profile مبكر.
4. Supervisor المصرّح يقبل الطلب؛ غير المصرّح له ومستخدم مؤسسة أخرى يُرفضان.
5. القبول ينشئ ملف طالب واحدًا، والتكرار لا يضاعفه، ولا يحدث تسكين ضمني.
6. التسكين قبل القبول، أو في مؤسسة أخرى، أو مجموعة ممتلئة/غير مؤهلة يُرفض.
7. التسكين الصحيح ينشئ Enrollment وMembership الصحيحين ويظهر الطالب في صفحة المجموعة.
8. Query الإتاحة المشتركة يعطي نتيجة صحيحة مع timezone/recurrence/exceptions.
9. كل قبول/رفض/تعليق/تسكين يترك Audit موثوقًا.
10. ملف Excel صالح يستورد بياناته مرة واحدة، والملف التالف/العابر للمؤسسة يعرض أخطاء
    ولا يترك كتابة جزئية مضللة.
11. اختبارات الأحداث الستة تثبت payload والعزل وidempotency ولا تستخدم Models عابرة.
12. اختبارات Policies/tenant isolation، Architecture/table ownership، migrations وrollback تمر.
13. رحلة المتصفح السابقة تعمل يدويًا بالعربية RTL، لا HTTP فقط.
