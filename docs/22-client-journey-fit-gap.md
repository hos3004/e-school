## 3. الفجوات مصنّفة حسب طبيعتها

### 3.1 فجوة البيانات — التصنيف لا يملك مدخلاته

النظام يوزّع اليوم على أساس أربعة معطيات فقط: العمر، الجنس، الدولة، المنطقة.
الرحلة تطلب التوزيع على أساس **أحد عشر معطى**. المفقود:

**مشترك:**
- إتاحة الطالب (المواعيد المناسبة) — لا يوجد جدول `student_availability` ولا
  إتاحة على مستوى الطلب قبل إنشاء الملف.

**مسار فصول الأطفال:**
- مقدار الحفظ من القرآن
- مستوى القراءة والكتابة بالعربية
- الاحتياج لمعاملة خاصة / صعوبات التعلم

**مسار مجالس التحفيظ:**
- الهدف: بدء الحفظ · استكمال · تثبيت · إجازة
- عند اختيار «إجازة» تتفرّع خمسة أسئلة: ختم القرآن · مدى التثبيت · الإجازات
  الحالية في القراءات · قدرة الحفظ في اللقاء الواحد · عدد اللقاءات أسبوعيًا

**المعلم:**
- خاتم للقرآن (نعم/لا) · مدى التثبيت · الإجازات المجاز/المجيز بها ·
  مستوى إتقان منهج نور البيان (لا أعرف · خلفية بسيطة · جيد · ممتاز)

**القرار التصميمي الموصى به:** الأعمدة التي **يستعلم عنها محرك المطابقة** تكون
أعمدة مكتوبة بأنواع Enum (المسار، الهدف، مستوى القراءة، مستوى الحفظ، الجنس،
الاحتياج الخاص، مستوى نور البيان). الأسئلة المتفرّعة النادرة (تفاصيل الإجازة)
تُخزَّن في `answers` jsonb مع تعريف النموذج في `config/admission.php`.
هذا يحترم قاعدة «قواعد العمل في config لا في الكود» ويتجنّب Rules Engine عامًا.

### 3.2 فجوة الخوارزمية — لا يوجد محرك مطابقة

`config/admission.php` يحمل بالفعل عقد المطابقة كاملًا:

```php
'matching' => [
    'gender_rule_values' => ['same', 'any'],
    'requires_availability_overlap' => true,
    'min_overlap_minutes' => 30,
    'automatic_ranking_enabled' => false,   // ← لم يُنفَّذ
],
```

لكن **لا توجد خدمة واحدة على القرص تنفّذه**. المطلوب `StudentPlacementMatcher`
داخل موديول `Enrollments` يقرأ عبر عقود القراءة (لا joins عابرة) ويُرجع ترتيبًا
مُعلَّلًا للمرشحين:

| المعيار | المصدر | نوعه |
|---------|--------|------|
| تطابق الجنس | قاعدة البرنامج + `staff_profiles.gender` | **حاجب** |
| تداخل الإتاحة ≥ الحد الأدنى | إتاحة الطالب × `teacher_availability` | **حاجب** |
| سعة المجموعة | `groups.capacity` (القيد الحالي 1–25) | **حاجب** |
| تأهيل المعلم للدورة | `teacher_courses` | **حاجب** |
| الأهلية للبرنامج | `EligibilityEvaluator` | **حاجب/تحذيري حسب config** |
| تقارب الأعمار داخل المجموعة | تواريخ ميلاد الأعضاء | **ترجيحي** |
| تقارب مستوى القراءة | حقل جديد | **ترجيحي** |
| تقارب مقدار الحفظ | حقل جديد | **ترجيحي** |
| توافق الهدف (تثبيت/إجازة/…) | حقل جديد | **ترجيحي** |
| المنطقة الزمنية | `groups.timezone` مقابل دولة الطالب | **ترجيحي** |

الأوزان في `config/admission.php`، والنتيجة **اقتراح مُعلَّل** لا قرارًا نهائيًا —
المشرف يعتمد أو يتجاوز بسبب مكتوب يدخل `audit_log`. الخيارات الثلاثة التي ذكرتها
ليست ثلاثة أنظمة: هي **ثلاث واجهات فوق نفس المحرك** (بوابة الطالب · ترشيح تلقائي ·
شاشة المشرف).

### 3.3 فجوة الكيانات الجديدة

سبعة كيانات غائبة تمامًا، ولكل منها مالك واضح ضمن الـ27 موديول القائم — **لا حاجة
لموديول جديد**:

| الكيان | المالك المقترح | يخدم |
|--------|----------------|------|
| `student_availability` | Students | المطابقة والجدولة |
| `teacher_applications` + التقييمات | Staff | توظيف المعلمين |
| `interviews` | Staff (مع ربط اختياري بـ VirtualClassroom) | مقابلات التوظيف · تقييم الطلاب · اجتماعات الإشراف |
| `supervisor_assignments` | AccessControl أو Organization | حصر نطاق مشرف الجودة |
| `curriculum_plans` + `curriculum_items` + `curriculum_progress` | Content | خطة المنهج وتتبّع الإنجاز |
| `support_tickets` + الردود | Messaging | تذاكر المعلمين والطلاب |
| `report_reviews` (تعليق المشرف) | AcademicReports | التعليق على تقارير الحصص |

### 3.4 فجوة النطاق والصلاحيات — مشرف الجودة

هذه أهم فجوة معمارية في الرحلة كلها. اليوم دور `academic_supervisor` يرى **كل**
طلاب ومجموعات المؤسسة. الرحلة تطلب أن يكون لكل مشرف جودة **نطاق محدد**.

التنفيذ الصحيح ليس فحص دور في الكود (ممنوع بالعقد)، بل:

1. جدول `supervisor_assignments (supervisor_user_id, scope_type, scope_id)` حيث
   `scope_type ∈ {group, program, teacher, student}`.
2. Global Scope على استعلامات القراءة يقيّد النتائج بنطاق المشرف الحالي.
3. صلاحية `supervision.scope.bypass` للمشرف العام والأدمن — تُمنح لا تُفترض.
4. كل تجاوز نطاق يدخل `audit_log`.

هذا يعمل جنبًا إلى جنب مع عزل `organization_id` القائم، ولا يستبدله.

## 4. إجابات مباشرة على الأسئلة المفتوحة

**١ — جدول منهج تفاعلي داخل الصف مع تظليل ما تم إنجازه؟**
نعم، وهو الأنسب معماريًا لأنه يربط ثلاثة أشياء موجودة بالفعل: الحصة، تقرير الحصة،
والمجموعة. البنية: `curriculum_plans` (خطة تُنشأ من قالب دورة أو تُبنى للمجموعة) →
`curriculum_items` (بنود مرتّبة) → `curriculum_progress` (حالة البند لكل مجموعة +
الحصة التي غُطّي فيها + من علّمه + متى). التظليل يصبح انعكاسًا للحالة لا حقلًا حرًا،
والمشرف يعلّق على البند نفسه. **اختياري لكل مجموعة** كما طُلب — مفتاح على المجموعة.

**٢ — توزيع الطلاب والمجموعات تحت مشرف جودة محدد؟**
نعم، وهو ضروري لا كمالي — انظر §3.4. بدونه تفقد المساءلة معناها مع الأعداد الكبيرة،
ويصبح كل مشرف مسؤولًا نظريًا عن الكل وعمليًا عن لا أحد.

**٣ — خاصية جدولة المقابلات؟**
نعم. الملاحظة المهمة: لا تُبنى ثلاثة أنظمة مقابلات. كيان `interviews` واحد بـ
`type` يغطي: مقابلة توظيف معلم · مقابلة تقييم طالب قبل التسكين · اجتماع إشرافي.
الثلاثة لها نفس البنية (مضيف · مدعو · موعد · غرفة · نتيجة · ملاحظات)،
وتستطيع إعادة استخدام `VirtualClassroomProvider` القائم لتوليد الغرفة.

**٤ — إرسال بريد إذا لم تكن هناك جلسة نشطة لصاحب الحساب؟**
نعم، ولكن ليس بالشكل الحالي. اليوم `config/notifications.php` يحدد القنوات **حسب
نوع الحدث ثابتًا** (`message_received` = in_app + push فقط). المطلوب قاعدة تصعيد:
الإشعار يبقى في الصندوق، وإذا مضت مدة قابلة للضبط ولم يُقرأ **والمستخدم غير متصل**،
يُصعَّد إلى البريد. يحتاج: تتبّع آخر ظهور للمستخدم + حقل `escalate_after_minutes`
في الصندوق + أمر مجدول. البنية القائمة (Outbox + محاولات التسليم + ساعات الهدوء)
تستوعب هذا بلا إعادة بناء.

**٥ — الموعد الأولي ثم يتفق المعلم والطالب على المواعيد؟**
هذه حالة واقعية يجب أن تُنمذَج صراحةً وإلا تحوّلت إلى فوضى في الواتساب. المقترح:
حالة `provisional` على الجدول، مع مهلة قابلة للضبط، ونافذة اتفاق داخل المراسلة
الجماعية للصف، وتثبيت نهائي بيد الإشراف يدخل `audit_log`. بلا هذا سيبقى النظام
يعرض موعدًا يعرف الجميع أنه غير حقيقي.

## 5. التعارضات — القرارات المعتمدة (2026-08-24)

## 7. عمل منفَّذ خارج ترقيم الحزم — بوابتا الطالب والمعلم (2026-08-24)

قبل بدء J-1، أُكملت صفحات بوابتَي الطالب والمعلم ورُبطت مسارات الكتابة الغائبة.
التفصيل الكامل والأدلة في `docs/page-completion-matrix.md` §8، وأهم ما فيه:

- **السبب الجذري:** مجموعة `api` بلا جلسة، ومسارات الموديولات خلف `auth:sanctum`
  تُرجع JSON — فكل نموذج كتابة في البوابات كان يُرفض 401. أُضيفت مسارات كتابة
  داخل `web` تستدعي نفس Application Actions.
- **ثلاثة عيوب إنتاجية اكتُشفت وأُصلحت**، أبرزها أن **تسليم التكليفات لم يعمل
  قط** بسبب مرجع enum خاطئ في النموذج وعمود `attachments` بلا default.
- المتبقي في هاتين البوابتين مرتبط بالحزم نفسها: إتاحة الطالب (J-1)، جدول المنهج
  (J-5)، التذاكر (J-6)، كشف الأجر (J-10).
